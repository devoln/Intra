# Decision

## What Was Decided

Переопределение программы канала, пришедшее из веб-UI (`SourceSendMidiEvent` с
статусом `0xC0`), считается РУЧНЫМ решением: вместе с ним поднимается флаг
`MidiSynth::mChannelProgramForced[channel]`, и пока флаг стоит, событие Program
Change ИЗ MIDI-ПОТОКА на этом канале полностью игнорируется — оно не меняет
инструмент и не отправляет обратную связь в UI. Снятие — выбор «Исходный из
файла», то есть `0xC0` со значением `0xFF`.

## Context

Владелец: «в celine заменяю Pan Flute на Flute, включаю полную генерацию с
замером, но всё равно играет Pan Flute. Даже если файл сам содержит событие,
которое заменяет инструмент, надо это блокировать. Ручной выбор инструмента
должен форсить его и игнорить любые переключения инструментов на канале.»

До правки `OnProgramChange` (файл и живой ввод) писал в ту же
`mChannelProgramOverride[channel]`, что и UI. Поэтому ручной выбор жил до
первого события программы в файле, после чего дорожка снова играла свой
инструмент — и в реальном времени, и в полной генерации (UI перед рендером
заново посылает переопределения, но файл перебивал их на первых тактах).

## Options Considered

- `A:` Правка только в UI (web): после выбора не показывать/не пересоздавать
  источник и фильтровать события файла на стороне JS. Не работает: событийный
  поток файла идёт из C++, а полная генерация поднимает свежий источник
  `SourceCreateFromMidiFileData` — фильтровать там было бы нечем.
- `B:` Отдельное «сильное» переопределение в движке (принято).
- `C:` Гасить инструмент файла фильтром событий при разборе MIDI. Хуже: темп и
  порядок событий меняются, ломается перемотка (`Midi::TrackCombiner`), а
  корректный выбор зависит от момента, когда пользователь нажал селектор.

## Why This Path Was Chosen

- Требование владельца буквально про приоритет: ручной выбор выше файла.
- Одна точка решения — `SetChannelProgram` (путь UI) и ранний выход в
  `OnProgramChange` (путь файла/живого ввода); состояние — 16 байт (`bool[16]`).
- Снятие форса уже существующим механизмом `0xFF` (в UI — «Исходный из файла»),
  новых элементов управления не появилось.

## Consequences

- Проще: расхождение «в селекторе Flute, играет Pan Flute» стало невозможным.
- Сложнее: у источника появилось состояние, которого нет в MIDI-файле; при
  пересоздании источника его надо восстанавливать (UI уже делает это через
  `applyTrackOverrides`).
- Новое ограничение: файловые Program Change на форсированном канале не видны и
  в UI-метрах (обратная связь не отправляется) — это сознательно: селектор не
  должен «перепрыгивать» сам.
- Живой ввод через `SendMidiEvent` (в т.ч. экранная клавиатура и Web MIDI) тоже
  поднимает форс — для источника без файла это безвредно.

## What Should Change Downstream

- Если появится понятие «вернуть управление файлу с текущего момента», точка
  уже есть: `0xFF` в `SetChannelProgram`.
- Документацию поведения стоит держать рядом с UI-кодом селектора
  (`web/synth.js`, `applyTrackOverrides`).

## Review Notes

- `RISK:` состояние форса живёт только в C++ и теряется при пересоздании
  источника; принято, потому что UI и так переслает выбор при каждом пересоздании.
- `NOTE:` проверка — `.scratch/force-instrument.mjs` (файл объявляет 75 и 73,
  форс 43 держит обе ноты на 43; после `0xFF` вторая нота снова 73).
